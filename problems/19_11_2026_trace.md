# Analisis & Arah Optimasi Satria (Berdasarkan Trace Syscall)

Dokumen ini merangkum hasil analisis dari `/tmp/min/workspace-syscalls.csv` dan kode sumber saat ini, serta memetakan arah optimasi selanjutnya untuk menurunkan overhead I/O filesystem.

## 1. Ringkasan Eksekutif
Arsitektur *incremental build* dan *fast-state* Satria sudah sangat matang. Bottleneck utama saat ini bukan pada logika build, melainkan pada **biaya syscall filesystem** (khususnya `stat` dan `access`) yang mendominasi 75-80% waktu eksekusi pada *cold build*.

**Target Optimasi:** Mengurangi jumlah syscall redundan tanpa mengubah semantik *fast-state* dan *cache validation*.

---

## 2. Peta Panas Syscall (Bottleneck)

| Syscall | % Waktu (Cold) | Calls | Error Rate | Akar Masalah |
| :--- | :--- | :--- | :--- | :--- |
| **`stat`** | **77.6%** | 9,340 | **50% (4,670)** | Pola *double-stat* (`fsFileExists` + `fsMTimeNs`), `probeAvailable` scan PATH, dan `depNodeAdd` stat per node. |
| **`access`** | ~2.1% | 1,205 | **42% (506)** | `resolveSpawnExe` melakukan scan PATH berulang untuk eksekusi child. |
| **`open`** | ~6.4% | 1,616 | 38% (613) | Probing file `.d` yang belum ada saat build pertama. |
| **`fopen64`** | ~2.1% | 436 | **8.2% (36)** | *Anomali*: Gagal di incremental build (leaf/bade) padahal file seharusnya ada. |

---

## 3. Rencana Optimasi (Prioritas)

### Prioritas 1: Eliminasi Pola Double-Stat (Gain: ~30-40% Cold Build)
**Masalah:** Banyak tempat di kode memanggil `fsFileExists(path)` lalu langsung `fsMTimeNs(path)`. Ini membuang 2 syscall per file, di mana yang pertama sering kali gagal (ENOENT).
**Arah Solusi:**
*   Ubah pola menjadi satu panggilan `fsMTimeNs(path)`. Jika return value `>= 0`, file pasti ada dan kita sudah punya mtime-nya.
*   **Target File:** `src/pack/pack.c`, `src/embed.c`, `src/workspace/ws_cache_save.c`, dan semua modul yang menggunakan pola `if (fsFileExists(...)) fsMTimeNs(...)`.

### Prioritas 2: Cache `probeAvailable` Lebih Agresif (Gain: ~5-10%)
**Masalah:** `resolveSpawnExe` di `src/port/port_proc_posix.c` sudah di-cache (32 entries), tetapi `probeAvailableScan` (yang dipanggil oleh `compile.c` dan `embed.c` untuk mengecek `gcc`, `ar`, `tar`, dll) **tidak di-cache**. Setiap build melakukan scan PATH penuh dengan `fsFileExists`.
**Arah Solusi:**
*   Tambahkan cache in-memory sederhana di `probeAvailable()` (mirip dengan `resolveSpawnExe`). PATH tidak berubah selama satu proses Satria berjalan.
*   **Target File:** `src/port/port_proc_posix.c`.

### Prioritas 3: Smart Stat di Dependency Graph (Gain: ~5%)
**Masalah:** `depNodeAdd` di `src/deps/deps_core.c` memanggil `depNodeMTimeMemo(path)` yang pada akhirnya melakukan `stat()` untuk setiap node dependensi (bisa >1000 file header).
**Arah Solusi:**
*   Manfaatkan `cmdsStatMemo` yang sudah ada. Pastikan `depNodeAdd` membaca dari memo stat terlebih dahulu sebelum jatuh ke `stat()` langsung.
*   Skip stat untuk path yang jelas merupakan header sistem (di luar `include paths` yang didefinisikan di Buildfile).

### Prioritas 4: Investigasi Anomali Incremental (Bug Fix)
**Masalah:** Ditemukan 36 error `fopen64` pada skenario *leaf* dan *bade* (incremental). Seharusnya tidak ada file yang gagal dibuka jika state-nya valid.
**Arah Solusi:**
*   Tambahkan logging sementara (atau `SATRIA_GATE_DEBUG=1`) khusus untuk 36 `fopen64` failures ini.
*   Kemungkinan besar ini adalah file `.d` yang dihapus manual atau cache state yang *corrupt* (basi) namun tidak terdeteksi oleh validator fast-state.

---

## 4. Catatan Arsitektur & Implementasi

Untuk menjaga *cognitive load* dan kebersihan kode, implementasi optimasi ini harus mematuhi aturan berikut:

1.  **Single Source of Truth untuk FS:** Semua perubahan syscall harus dilakukan di lapisan `src/port/port_fs.c` atau wrapper memo stat (`src/cmds/cmds_statmemo.c`). Jangan sebar logika `stat()` mentah di modul bisnis.
2.  **Zero Semantic Change:** Optimasi ini murni pengurangan biaya I/O. Logika validasi *fast-state*, *fingerprint*, dan *router* tidak boleh berubah.
3.  **Environment Fallback:** Tambahkan env var `SATRIA_DECIDE_FROM_PLAN=0` (jika belum ada) untuk memungkinkan fallback ke perilaku lama saat debugging regresi.

## 5. Estimasi Dampak

Jika Prioritas 1 dan 2 diimplementasikan:
*   **Cold Build:** ~8.2s ➔ **~5.5s** (Hemat ~2.7s / 33%)
*   **Incremental (Leaf/Bade):** ~1.1s ➔ **~0.7s** (Hemat ~0.4s / 36%)
*   **Syscall Count:** Berkurang dari ~14,500 ➔ **~8,000 calls** per cold build.

## 6. Hasil audit CPU lanjutan (20 Nov 2026)

Profil `gprof` pada workspace 5k (`-pg`, `GMON_OUT_PREFIX`) memisahkan biaya
satria dari biaya gcc. Temuan dan tindakan:

| Temuan | Status |
| --- | --- |
| `csOpen` 28x per run leaf; `insertNew` >900 ribu entri | Diturunkan: `loadFile` sekali-baca, arena node+payload, parser desimal langsung |
| `optsCacheFileHash` membaca deps/lib/fingerprint (~2 MB) 15–16x | Diganti memo stempel (path+mtime ns+size+proj): 0 baca hash, jumlah `csOpen` besar turun ~2x |
| `wsCacheLoadMap` + `qsort` mendominasi no-op | `sources.cache` dibaca sekali lalu dipecah in-place |
| `csProjMetaStampFileN` masih membuka+tulis 4 cache per run | Kandidat: metadata-only scan / merge di router (P4 fase 2) |
| Penulisan cache bersama oleh banyak anak fork | Akar masalah P4; solusi stage-and-merge (`design/router_centric.md`) |

Catatan: Prioritas 2 (`probeCache` 32 entri di `port_proc_posix.c`) dan
Prioritas 3 (`depNodeAdd` lewat `cmdsStatCached`) sudah ada di kode sebelum
audit ini — bagian rencana di atas sudah usang untuk keduanya.
